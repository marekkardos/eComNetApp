  Detailed Discussion

  1. Token:Audience - Should You Enable It?

  What Audience validation does:
  The aud (audience) claim identifies the recipients the JWT is intended for. When enabled, the API would reject tokens that don't have a matching audience.

  Arguments FOR enabling it:
  - Security best practice - ensures tokens intended for one API can't be used at another
  - Useful if you ever have multiple APIs/services sharing the same signing key
  - Completes the JWT validation pattern (issuer + audience + signature)

  Arguments AGAINST enabling it:
  - For a single API application, it adds complexity with limited security benefit
  - If you get the audience value wrong, valid tokens get rejected
  - Adds another configuration value to manage across environments

  Current risk of NOT having it:
  - Minimal for a single-API application
  - The signing key already ensures only your API can validate tokens

  2. Token:Issuer Port Discrepancy - Actual Impact

  How issuer validation works:
  1. TokenService creates token with iss = "http://localhost:5001" (from config)
  2. When validating incoming tokens, ValidIssuer = "http://localhost:5001" must match

  The "gotcha":
  Since both creation AND validation use the same config value (Token:Issuer), tokens will still validate correctly even with the "wrong" port - they're consistently wrong on both sides.

  When this becomes a problem:
  - If you have multiple API instances with different Token:Issuer configs - tokens from one won't validate on the other
  - If you change Token:Issuer while tokens are still in circulation - old tokens stop working
  - Semantic incorrectness - the issuer claim should technically identify "who issued the token"

  Container behavior:
  With ASPNETCORE_ENVIRONMENT=Development in docker-compose.yml, the container uses appsettings.Development.json, so it uses localhost:5001 even though it's running on port 44369.

  3. Potential Approaches

  Option A: Environment-specific configuration
  Create appsettings.Docker.json or use environment variables in docker-compose:
  environment:
    - Token__Issuer=http://localhost:44369

  Option B: Accept the semantic incorrectness
  Keep it as-is since validation still works (both sides use the same value)

  Option C: Use a non-port-specific issuer
  Change to something like "Issuer": "eComNetApp" - an identifier rather than a URL

  Option D: Remove Issuer validation entirely
  Set ValidateIssuer = false (less secure but simpler)
